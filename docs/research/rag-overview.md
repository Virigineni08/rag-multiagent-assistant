## RAG Ingestion Pipeline
1. Document Upload      → FastAPI (file upload endpoint receives the file from the user)
2. Text Extraction      → PyMuPDF (PDF), python-docx (DOCX), pandas (CSV), Python built-in file read (TXT)
3. Cleaning/Normalization → Plain Python (regex/string operations to strip whitespace, headers, footers)
4. Chunking              → LangChain text splitters (e.g. RecursiveCharacterTextSplitter)
5. Embedding Generation  → OpenAI Embeddings API (via langchain-openai)
6. Vector Store Indexing → ChromaDB
## RAG Query Pipeline
Embeddings encode meaning using coordinates in a vector space, but various embedding models have different spaces in which the same text is embedded, much like two distinct coordinate spaces that cannot be compared. Using different embedding models for the query and the chunks would render similarity measures meaningless because "distance" in one embedding space does not necessarily translate to distance in another. Thus, using the same model will ensure that the query and the chunks are placed in the same embedding space.
## Embeddings
The limitation of traditional keyword matching is that it looks for an exact match. So, if a person asks "How do I cancel my membership?", but the document has "terminate your subscription", then traditional keyword matching will not help at all because the meanings are exactly the same. However, using semantic search based on embeddings would be beneficial because the vectors for "cancel membership" and "terminate subscription" would be similar to each other although there would be no common words.
## Vector Databases
The vector database is unlike the regular database, such as SQLite, since SQLite is designed to work better with the exact query (WHERE clauses, joins), whereas the vector database is designed to find similarities within the high dimensional embeddings. In our case, the ChromaDB will store the embedding of each chunk in addition to the metadata such as which document it was extracted from and the chunk number and return back the most similar chunks when a query is made.
## Semantic Search
Semantic search involves the creation of an embedding of the query inputted by the user, which is then compared to the document embeddings already stored using cosine similarity or some other similar metric to retrieve the most semantically relevant chunks irrespective of their semantic overlap. In our case, this takes place in the Retrieval Agent, which invokes ChromaDB for retrieving the top-K chunks with the most similar embedding to the query.
## Chunking Strategies
Chunking involves breaking down the document into smaller parts prior to the embedding process since embedding models as well as the LLM context window perform better with concentrated text as opposed to whole documents; chunking enables retrieval to extract precisely that part of the document that is required instead of the entire document. Overlapping chunks (such as 150 tokens) will be used to ensure that there isn’t any context lost when the idea or sentence is split between the two chunks.
## Retrieval (Top-K & Evaluation)
Retrieval fetches the top-K most similar chunks (rather than just the one) because the right answer can potentially be found in multiple chunks, and having several possibilities to choose from will make life easier for the LLM. The quality of the retrieval is measured through Top-1, Top-3, and Top-5 accuracies, i.e., whether the known chunk containing the right answer was among those selected, and in particular, “unavailable information” is tested to rule out any hallucinations on the part of the model.
## Prompt / Context Construction
Context construction refers to the process through which the chunks that have been retrieved are used to form the prompt for the large language model, including how the chunks are ordered, labeled, and the amount of context budget allocated to them, together with instructions on what the model should do using the provided context without hallucinating. It is important to have good context construction since the retrieval of proper chunks may still be wasted if the prompts are not structured well.
## Chunking Strategy
The chunking strategy involves the breaking down of source documents into smaller chunks prior to the process of embedding. The balance here is between chunk sizes (smaller chunks risk losing contextual information, while bigger chunks dilute the embedding since a single vector ends up representing multiple topics rather than a single topic) and overlapping (replicating a piece of text between consecutive chunks to ensure that no information gets orphaned near a boundary). There are various ways to split the document: fixed-size splitting (splitting documents every N tokens independently of content, which might result in splitting sentences or tables), structure-aware splitting (prioritizing splitting according to structures like headings and paragraphs), and semantic splitting (splitting by topic shift). In many cases, poor chunking is actually the main reason why a query fails to retrieve an answer – when a chunk boundary splits a query from its answer, no tuning and prompt engineering will help retrieve it since the answer wasn’t ever stored in the document as one entity.
## Embedding Models
The Embedding Model transforms the text data into a vector of fixed length through contrastive learning approach, which brings the semantically related texts close to each other and pushes apart the unrelated texts in the vector space. The selection of model depends on certain factors such as dimension, suitability of the model for the domain and maximum input length, but the key consideration while selecting the model is the consistency, because the same model should be used to embed the stored chunks and new queries, otherwise, it will not work at all.
